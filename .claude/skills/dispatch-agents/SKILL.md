# 멀티 에이전트 디스패치

현재 세션(control-agent)이 외부 리포의 Claude Code 에이전트(worker-agent)에게 `claude -p`로 작업을 위임하고, 결과를 수집해 중앙에서 추적하는 워크플로우.

```
control-agent (현재 세션)
  ├── claude -p → worker-agent A (리포 A)
  ├── claude -p → worker-agent B (리포 B)
  └── 거버넌스 · Phase 개요 · QA · 대시보드 관리
```

**전체 흐름:**

```
[0] 권한 확인 → [1] 컨텍스트 파악 → [2] Phase 설계 → [3] WO 작성 → [4] 디스패치 → [5] 결과 수집·QA 검증 → [6] 종합 보고
```

---

## Step 0: 권한 모드 확인 (최초 1회)

worker-agent는 `claude -p`(비대화형)로 실행되므로 권한 승인 프롬프트에 막힐 수 있다.
기본적으로 `--dangerously-skip-permissions`를 사용한다.

사용자에게 **한 번만** 확인:

> worker-agent 실행 시 `--dangerously-skip-permissions` 플래그를 사용합니다 (비대화형 실행에 필요).
> 이 모드를 사용하지 않으려면 알려주세요. 대신 대화형 세션(사용자가 직접 터미널에서 claude 실행)으로 전환합니다.

사용자가 거부하면 → Step 4에서 `claude -p` 대신 **대화형 프롬프트 제공** 모드로 전환한다.
(사용자에게 터미널 명령어와 프롬프트를 알려주고, 결과를 직접 전달받는 방식)

이 확인은 세션당 1회만 한다. 이후 디스패치에서는 같은 설정을 재사용.

`$ARGUMENTS`에서 아래 정보를 추출한다:

| 항목              | 필수 | 예시                                                   |
| ----------------- | ---- | ------------------------------------------------------ |

| 작업 설명         | 택1  | "staleness TTL 추가"                                   |
| 거버넌스 디렉토리 | 선택 | 기존 work_order_and_progress 경로 (없으면 생략 가능)   |

**분기:**

- 작업 설명만 주어지면 → Step 2 (Phase 설계)
- 둘 다 없으면 → 사용자에게 질문

## Step 2: Phase 설계 (필수)

WO를 작성하기 전에, **전체 그림**을 먼저 그린다. Phase 개요 없이 WO부터 만들면 개별 작업은 진행되지만 전체 방향성과 성공 기준이 모호해진다. 이 단계는 "무엇을 왜 하는가"와 "어떻게 되면 성공인가"를 명문화하는 것이다.

### 2-1. Phase 개요 작성 (`00_overview.md`)

피처 폴더에 Phase 개요를 **필수로** 작성한다. 이 문서가 없으면 WO 작성(Step 3)으로 넘어가지 않는다.

```markdown
# Phase 개요: {제목}

> 작성일: {YYYY-MM-DD}
> 대상 리포: {리포 목록}
> 에이전트: {에이전트 목록}

## 1. 배경 및 목적

<!-- 왜 이 작업이 필요한가. 어떤 문제를 해결하거나, 어떤 가치를 만드는가. -->
<!-- 사용자의 원래 요청을 그대로 옮기지 말고, 맥락을 포함해서 서술한다. -->

## 2. Phase 구조

| Phase | 목표 | 주요 변경 | 대상 에이전트 | 선행 조건 |
| ----- | ---- | --------- | ------------- | --------- |
| P0    | ...  | ...       | ...           | 없음      |
| P1    | ...  | ...       | ...           | P0 완료   |
| P2    | ...  | ...       | ...           | P1 완료   |

## 3. Phase 간 의존성

<!-- Phase 순서가 왜 이런지, 어떤 Phase가 독립 실행 가능한지 -->
<!-- 병렬 가능한 Phase가 있으면 명시 -->

## 4. 전체 완료 기준

<!-- 모든 Phase가 끝났을 때 시스템이 어떤 상태여야 하는가 -->
<!-- 기능적 기준과 비기능적 기준 모두 포함 -->

- [ ] ...
- [ ] ...
```

**작성 가이드:**

- §1(배경 및 목적): 한 문단이면 충분하다. 다만 "왜"가 빠지면 안 된다
- §2(Phase 구조): 테이블로 전체 Phase를 한눈에 보여준다. Phase 수는 작업 규모에 따라 유동적
- §3(의존성): Phase 간 순서가 있는 이유를 설명. 병렬 가능하면 명시하여 디스패치 효율을 높임
- §4(완료 기준): Step 5의 QA 검증에서 이 기준을 대조한다. 모호하면 QA가 형식적이 됨

### 2-2. QA 기준 수립 (`00_qa-criteria.md`)

Phase 개요와 함께 **사전 QA 기준**을 필수로 작성한다. 작업을 시작하기 전에 "어떻게 되면 성공인가"를 구체화해야, 디스패치 후 결과를 객관적으로 판정할 수 있다.

```markdown
# QA 기준: {제목}

> 작성일: {YYYY-MM-DD}
> 기반: 00_overview.md

## Phase별 검증 기준

### Phase {N}: {목표}

| #   | 검증 항목 | 기대 결과 | 검증 방법  | 우선순위 |
| --- | --------- | --------- | ---------- | -------- |
| Q1  | ...       | ...       | 빌드 로그  | 필수     |
| Q2  | ...       | ...       | 수동 확인  | 필수     |
| Q3  | ...       | ...       | E2E 테스트 | 권장     |

### Phase {N+1}: {목표}

| #   | 검증 항목 | 기대 결과 | 검증 방법 | 우선순위 |
| --- | --------- | --------- | --------- | -------- |

## 전체 품질 기준

### 기능적 기준

<!-- 사용자 관점에서 "이 기능이 동작한다"를 확인할 수 있는 항목 -->

- [ ] ...

### 비기능적 기준

<!-- 성능, 안정성, 코드 품질 등 -->

- [ ] 빌드 통과 (모든 리포)
- [ ] 린트 통과 (모든 리포)
- [ ] 기존 기능 회귀 없음
- [ ] ...
```

**작성 가이드:**

- 검증 항목은 **관찰 가능한 결과**로 기술한다 ("코드가 깔끔해야 한다" X → "콘솔 에러 0건" O)
- 검증 방법은 구체적으로: 빌드 로그, 특정 페이지 접속, API 호출, 콘솔 확인 등
- 우선순위는 `필수` / `권장` 두 단계. 필수 항목이 하나라도 실패하면 Phase 미완료 판정
- 전체 품질 기준의 기능적/비기능적 구분은 나중에 QA 보고서에서 누락 없이 점검하기 위함

### 2-3. 폴더 구조

Phase 설계 후 피처 폴더 구조:

WO가 없을 때 사용자 요구사항으로부터 작성한다. `00_overview.md`의 Phase 구조를 기반으로 Phase별 WO를 생성한다.

### WO 템플릿

```markdown
# WO-{ID}: {제목}

> 대상 에이전트: **{agent-name}** ({repo-name})
> 우선순위: {P0|P1|P2}
> 상태: ⬜ 대기
> 생성일: {YYYY-MM-DD}
> 완료일: -

## 1. 목적

{1-2줄 요약}

## 2. 컨텍스트

- 참조 문서: {경로들}

## 3. 상세 요구사항

{구체적 변경 사항 — worker-agent가 이것만 읽고 구현할 수 있을 정도로 구체적이어야 함}

## 4. 영향 파일 (예상)

| 파일 | 변경 유형 | 설명 |
| ---- | --------- | ---- |

## 5. 검증 기준

- [ ] 빌드 통과
- [ ] 린트 통과
- [ ] {기능별 검증 항목}

## 6. 주의사항

- {회귀 방지, 의존성, 주의할 패턴 등}

## 7. 결과 (작업 후 기록)

### 변경 파일

### 검증 결과

### 발견된 이슈

### 후속 작업
```

WO의 **§3 상세 요구사항**이 핵심이다. worker-agent는 비대화형이라 질문할 수 없으므로, 모호함 없이 작성해야 한다. 기존 코드 패턴 참조가 필요하면 파일 경로를 명시적으로 포함.

WO의 **§5 검증 기준**은 `00_qa-criteria.md`의 Phase별 기준과 정합해야 한다. QA 기준에 "Q2: 콘솔 에러 0건"이 있으면, 관련 WO의 §5에도 이에 대응하는 검증 항목이 있어야 한다.

## Step 4: 디스패치

### 4-1. 프롬프트 조립

```
다음 작업 지시서를 읽고 요구사항대로 구현하라.

작업 지시서: {WO 파일 절대경로}

실행 규칙:
1. WO 파일을 읽고 목적·요구사항을 파악
2. 관련 기존 코드를 탐색하여 패턴 파악
3. 요구사항대로 구현
4. 빌드 검증
5. 린트 검증
6. WO의 검증 기준 항목을 모두 확인

커밋하지 마라. 결과만 아래 형식으로 보고:
- 변경된 파일 목록 (경로 + 변경 유형)
- 빌드/린트 결과 (통과/실패 + 에러 내용)
- 검증 기준 충족 여부 (항목별)
- 발견된 이슈나 우려사항
```

### 4-2. 실행 명령

**skip-permissions 모드 (기본):**

```bash
cd {리포_절대경로} && claude -p "{프롬프트}" --dangerously-skip-permissions --output-format json 2>&1
```

**대화형 모드 (사용자가 skip-permissions 거부 시):**

사용자에게 아래 안내를 출력한다:

```
{agent-name} 실행 안내

터미널에서:
  cd {리포_절대경로}
  claude

프롬프트:
  {위에서 조립한 프롬프트}

완료 후 결과를 알려주세요.
```

### 4-3. 실행 전략

- **서로 다른 리포** → 병렬 실행 (`run_in_background: true`로 각각 Bash 호출)
- **같은 리포의 여러 WO** → 순차 실행 (파일 충돌 방지)
- 타임아웃: 작업 복잡도에 따라 조절. 기본 600000ms (10분). DB 마이그레이션 포함 시 더 길게.

### 4-4. 디스패치 직후

거버넌스 대시보드가 있으면 해당 WO 상태를 `🔵 진행중`으로 업데이트.

## Step 5: 결과 수집 및 QA 검증

### 5-1. 결과 파싱

`--output-format json` 결과에서:

- `result` 필드: 에이전트의 텍스트 보고
- 종료 코드: 성공/실패

### 5-2. 결과 기록

WO 파일의 `## 7. 결과` 섹션을 에이전트 보고 내용으로 업데이트.

### 5-3. 대시보드 갱신 (있는 경우)

- 성공: `✅ 완료`
- 실패: `🔴 실패` + 사유

### 5-4. 실패 대응

| 실패 유형      | 대응                              |
| -------------- | --------------------------------- |
| 빌드/린트 실패 | 에러 분석 → WO 보충 → 재디스패치  |
| 타임아웃       | WO 스코프 분할 검토               |
| 에이전트 오류  | 프롬프트 개선 후 재실행           |
| 2회 연속 실패  | 사용자에게 보고, 대화형 전환 제안 |

### 5-5. 후속사항 트리아지 — WO/Phase 완료 시마다 수행

worker-agent의 결과(WO §7)에는 "발견된 이슈"와 "후속 작업"이 포함된다. 이것들을 방치하면 쌓이기만 하고 정리되지 않는다. control-agent는 각 WO 완료 직후, 그리고 Phase 완료 시점에 후속사항을 **즉시 트리아지**하여 다음 세 가지로 분류한다:

| 분류                     | 기준                                                                                   | 행동                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **즉시 처리**            | 변경 범위가 작고(1~2파일), 현재 Phase 맥락 안에서 해결 가능하며, 다른 WO에 영향 없음   | 추가 WO 없이 바로 디스패치하거나 직접 수정. 완료 후 대시보드에 기록                |
| **후속 계획 추가**       | 현재 Phase 스코프 밖이거나, 별도 Phase/WO가 필요한 규모. 당장 안 해도 진행에 지장 없음 | `00_overview.md`의 Phase 구조에 반영하거나 새 WO 생성. 대시보드에 `⬜ 대기`로 추가 |
| **블로커 → 사용자 확인** | 설계 방향 결정, 외부 의존성, 스코프 변경 등 control-agent가 독단으로 판단할 수 없는 것 | 즉시 사용자에게 보고하고 판단을 요청. 결정 전까지 관련 후속 WO 보류                |

**트리아지 판단 기준:**

즉시 처리와 후속 계획의 경계가 애매할 때는 **"이걸 지금 안 하면 다음 Phase에서 문제가 되는가?"**로 판단한다. 그렇다면 즉시 처리, 아니면 후속 계획이다.

블로커 판단의 핵심은 **"되돌리기 어려운 결정인가"**이다. 코드 수준의 선택(이 함수를 이 패턴으로 구현)은 control-agent가 판단해도 되지만, 아키텍처 방향 전환이나 스코프 확대는 사용자 확인이 필요하다.

**트리아지 실행 시점:**

1. **WO 단위**: 각 WO 결과 수신 직후, §7의 "발견된 이슈"와 "후속 작업"을 트리아지한다. "즉시 처리" 항목이 있으면 다음 WO 디스패치 전에 처리한다.
2. **Phase 단위**: Phase의 모든 WO 완료 후, 전체 후속사항을 재점검한다. WO 단위에서 "후속 계획"으로 분류했던 것 중 Phase 결과를 보니 지금 해야 하는 것이 있을 수 있다.

**트리아지 결과 기록:**

대시보드나 QA 보고서에 트리아지 결과를 남긴다:

```
## 후속사항 트리아지 (Phase {N} 완료 시점)

### 즉시 처리 (완료)
- [WO-P1-01] 타입 export 누락 → 즉시 수정 완료

### 후속 계획 추가
- [WO-P1-02] 에러 바운더리 통합 → Phase 3에 WO-P3-01로 추가
- [WO-P1-03] 성능 최적화 여지 → Phase 3에 WO-P3-02로 추가

### 블로커 (사용자 확인 대기)
- [WO-P1-02] 상태 관리 패턴을 Context에서 Zustand로 전환할지 → 사용자 결정 필요
```

### 5-6. QA 검증 (`00_qa-report.md`) — Phase 완료 시 필수

해당 Phase의 모든 WO가 완료되고 후속사항 트리아지의 "즉시 처리" 항목까지 해결되면, `00_qa-criteria.md`의 기준을 하나씩 대조하여 QA 보고서를 작성한다. 트리아지에서 "즉시 처리"한 항목도 QA 범위에 포함한다.

**QA 보고서 작성 가이드:**

- §1: `00_qa-criteria.md`의 해당 Phase 테이블을 그대로 가져와서 실제 결과 칼럼만 채운다
- §2(의도 vs 결과): 가장 중요한 섹션. 단순 통과/실패를 넘어 "원래 하려던 것이 정말 되었는가"를 서술한다. WO 단위가 아니라 Phase의 목표 단위로 평가한다
- §3: FAIL 항목은 반드시 대응 방안을 기록. 다음 Phase로 넘기거나, 추가 WO를 생성하거나, 수용하는 경우 그 근거를 남긴다
- Phase FAIL 판정: 필수 항목 중 하나라도 실패하면 FAIL. 사용자에게 보고하고 대응 방향을 확인받는다

**전체 Phase 완료 시:**

마지막 Phase까지 끝나면, `00_qa-criteria.md`의 "전체 품질 기준" 섹션도 QA 보고서에 추가 검증한다. 이때 `00_overview.md`의 §4(전체 완료 기준)과도 대조한다.

## 설계 원칙

### WO가 프롬프트의 품질을 결정한다

`claude -p`는 한 번 보내고 끝이다. worker-agent가 중간에 질문할 수 없으므로, WO의 §3(상세 요구사항)이 충분히 구체적이지 않으면 결과물 품질이 떨어진다. 참조해야 할 기존 코드 패턴, 파일 경로, 빌드 명령어 등을 명시적으로 넣어라.

### Phase 개요가 방향을 잡고, QA 기준이 기준선을 잡는다

Phase 개요 없이 WO만 작성하면 "나무만 보고 숲을 못 보는" 상태가 된다. 개요는 전체 작업의 why와 구조를 담고, QA 기준은 "어디까지 가면 되는가"를 담는다. 이 둘이 있어야 WO의 범위와 우선순위를 올바르게 판단할 수 있고, 완료 후 성공 여부를 객관적으로 판정할 수 있다.

### 한 리포에 한 에이전트

같은 리포에 여러 에이전트를 동시에 돌리면 파일 수정이 충돌한다. 한 리포에는 한 번에 하나의 worker-agent만 실행.

### worker-agent는 커밋하지 않는다

코드 변경은 worker-agent가 하지만, 커밋은 control-agent가 결과를 확인한 후 사용자 승인을 받아 진행한다. `git -C {리포경로} ...`로 원격 커밋 가능.

### 거버넌스는 선택사항

단발성 디스패치에는 거버넌스 구조(00_governance.md, 01_dashboard.md)가 불필요할 수 있다. 여러 WO를 Phase 단위로 관리할 때만 생성하면 된다.

### QA는 Phase 단위로 반복한다

QA 보고서는 Phase가 끝날 때마다 작성한다. 마지막에 몰아서 쓰면 중간 Phase의 문제가 후속 Phase에 전파된다. Phase FAIL이면 다음 Phase로 넘어가기 전에 사용자와 대응 방향을 합의한다.

### 후속사항은 발견 즉시 분류한다

WO 결과에서 나온 "발견된 이슈"와 "후속 작업"을 방치하면 목록만 길어지고 아무도 정리하지 않게 된다. control-agent가 즉시 트리아지하여 사소한 것은 바로 처리하고, 규모가 있는 것은 계획에 반영하고, 판단이 필요한 것은 사용자에게 묻는다. 이 분류가 Phase 간 전환의 완결성을 높인다.

### 구조적 QA 검증을 반드시 포함한다

빌드/린트 통과만으로는 "기능이 동작한다"를 보장하지 못한다. 모든 디스패치 작업 완료 후 아래 3단계 QA를 수행한다:

**1단계: 코드 구조 맵 분석**
대상 코드를 읽고 구조 맵을 작성한다:

```
page.tsx
├── 탭: [탭1 ✅, 탭2 ✅, ...]
├── 버튼: [등록 ✅, 엑셀 ❌ (onClick 빈 함수), ...]
├── 모달: [FormDialog ✅, DetailDialog ⚠️ (import만, 미연결), ...]
└── API: GET /api/... → Service → Repository → DB ✅
```

기능 상태를 3가지로 판정:

- ✅ 완전 구현 (UI + API + DB 모두 연결)
- ⚠️ 부분 구현 (UI만 있고 onClick 빈 함수 등)
- ❌ 미구현 (컴포넌트 파일만 있고 import 안 됨)

**2단계: Playwright 자동 QA**
구조 맵에서 추출한 체크리스트로 Playwright 스크립트를 작성·실행한다:

- UI 존재 확인: 모든 탭, 버튼, 모달이 실제로 보이는지
- CRUD 동작: 실제로 등록/수정/삭제 + DB 확인
- 트랜잭션 체인: 모듈 간 데이터 흐름 (등록 → 다른 모듈에서 확인)

**3단계: FAIL → 수정 → 재테스트**
FAIL 항목을 수정 에이전트에 디스패치하고, 수정 후 해당 TC만 재실행한다.
트래커 파일(`qa-tracker.md`)에 TC별 PASS/FAIL을 기록하여 누락 방지.
